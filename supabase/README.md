# Supabase setup (optional)

**You do not need this.** Quantum Lab runs fully client-side and saves circuits to
your browser's `localStorage` when no Supabase project is configured. Everything —
the simulator, the presets, saving, loading and share links — works out of the box.

Configure Supabase only if you want **accounts**, **cross-device sync**, **billing**, **org
seats** or **server-graded certification exams**. Everything else works without it.

## 1. Create a free project

1. Go to <https://supabase.com> and sign up (the free tier is plenty).
2. Click **New project**, pick a name and a database password, and choose a region
   near you.
3. Wait a minute or two for the project to finish provisioning.

## 2. Find your URL and anon key

In the dashboard, open **Project Settings → API**. You need two values:

- **Project URL** — looks like `https://abcdefghijklm.supabase.co`
- **anon public** key — a long JWT string under *Project API keys*

The `anon` key is safe to ship in a browser bundle; row level security (below) is
what actually protects the data. Never use the `service_role` key in the frontend.

## 3. Run the schema

**Fastest path — the CLI.** The same files are also laid out as ordered
migrations in `supabase/migrations/` (generated by
`scripts/supabase-migrations.sh`; edit the `schema*.sql` files, then
regenerate). With the CLI linked to your project this applies all fifteen in
the right order, and re-running it is a no-op:

```bash
supabase login
supabase link --project-ref <your-project-ref>
supabase db push
```

The whole chain has been applied twice in sequence against a clean Postgres
16 with a stub of Supabase's `auth` schema — every file succeeds, every file
is idempotent, 29 tables result — so the "never run against a live project"
notes inside the individual files are now out of date on that point. What has
NOT been exercised is Supabase's own auth/RLS runtime against them, which
only a real project can do.

**Or by hand, in the SQL editor:**

Open **SQL Editor → New query**, paste the entire contents of
[`schema.sql`](./schema.sql), and click **Run**. It creates the `public.circuits`
table, its indexes, row level security policies, and an `updated_at` trigger. The
script is idempotent, so re-running it is safe.

That alone gives you accounts and saved circuits only. For everything else do NOT run the schema files one
by one: paste [`apply-all-migrations.sql`](./apply-all-migrations.sql) (all the schema files plus the
2026-10-22 audit migration, in order, idempotent), or run `supabase db push` to apply `migrations/`. Then
paste [`verify-migrations.sql`](./verify-migrations.sql); every row must read OK / no rows.

### Row level security — every table, no exceptions

The `anon` key is public by design, so **RLS is the only thing standing between a
browser and every row in the database**. Each schema file in this folder enables
it and writes its own policies:

There are **fifteen** schema files (`schema.sql`, `schema-billing.sql`, `schema-exams.sql`, `schema-orgs.sql`,
and eleven later ones, ending with `schema-hardening.sql`). They must run in the order
`scripts/supabase-migrations.sh` lists, because later ones reuse helpers earlier ones define, and
**`schema-hardening.sql` is not optional**: it stops any signed-in user minting a University org and
granting themselves EDU entitlement, removes the browser's direct circuit insert, withdraws the anon
leaderboard grant, and (Part E, audit 2026-10-22) caps seats in the database. Do not hand-pick files:

- **SQL editor:** paste `apply-all-migrations.sql` (everything, in order, idempotent).
- **CLI:** `supabase db push` applies `migrations/` (including `20261022000040_rls_audit_2026_10_22.sql`).

Then run `verify-migrations.sql`; every row must read OK and the "must return zero rows" queries must be empty.

Highlights of what the files enable, for orientation:

| File | Tables / functions | RLS |
| --- | --- | --- |
| `schema.sql` | `public.circuits` | on — own rows, plus public reads of `is_public` rows |
| `schema-billing.sql` | `subscriptions`, `hardware_usage`, `stripe_events`, `reserve_hardware_job()`, `apply_stripe_subscription()` | on — read your own row, **no user writes at all** |
| `schema-exams.sql` | `exam_attempts`, `exam_certificates` | on — own attempts; certificates are resolved by the public verify route through the service role |
| `schema-orgs.sql` | `orgs`, `org_members`, `org_invites`, `org_assignments`, `org_progress_consent`, `org_progress` | on — read your own org, owner/admin writes; invites are written by managers only |
| `schema-hardening.sql` | `user_progress`, seat-cap and invite-lock triggers | on |

`schema-exams.sql` was added after this README was first written and is easy to miss. Without it
the exam routes have no store and refuse a start rather than accepting an attempt they could not
grade — which is the safe direction, but it looks like the exams are broken.

**SECURITY DEFINER functions that take a user id (`spend_in_window`, `reserve_hardware_job*`) are
`service_role` only.** `DROP FUNCTION` discards grants and `CREATE FUNCTION` hands EXECUTE back to
PUBLIC (and to anon/authenticated on Supabase), so any file that drops and recreates one must re-apply
its revokes. `verify-migrations.sql` checks this.

**`subscriptions` has no user write policy at all, and that absence is the entire billing security
model.** A browser holding the anon key cannot set its own `plan_id`; only the webhook, running
with the service role, writes that column.

> **Re-running `schema-orgs.sql` deletes every unclaimed invite.** Deliberately — the old token
> scheme was forgeable, and hashing those tokens would preserve keys an attacker can compute.
> Export the pending invitations first (`docs/DEPLOYMENT.md` § 5.2) and re-send them from the
> admin console afterwards. On a fresh project the migration block does not run at all.

**The one table with no schema file here is the analytics sink.**
`/api/analytics` inserts into whatever table `ANALYTICS_SUPABASE_TABLE` names,
and ingestion is off unless an operator sets that variable. If you turn it on,
you are creating that table yourself — enable RLS on it in the same breath.
Events are written server-side with the service role, which bypasses RLS, so the
correct policy set is usually *none at all*: no select, no insert, no update, no
delete for `anon` or `authenticated`. A table with RLS enabled and zero policies
denies everyone except the service role, which is exactly what is wanted.

```sql
-- Template, if you add an analytics sink. Adjust the columns to match
-- the insert in apps/web/app/api/analytics/route.ts.
create table if not exists public.analytics_events (
  id         uuid primary key default gen_random_uuid(),
  name       text not null,
  at         timestamptz not null default now(),
  props      jsonb,
  session_id text
);

-- RLS on, no policies: only the service role (the API route) may touch it.
-- Without this line the anon key can read every event in the table.
alter table public.analytics_events enable row level security;
```

## 4. Configure the app

Create `apps/web/.env.local` (it is git-ignored) with:

```
NEXT_PUBLIC_SUPABASE_URL=https://abcdefghijklm.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOi...your-anon-key...
```

Restart the dev server (`npm run dev`) — Next.js only reads env files at startup. Both variables
are inlined at build time, so in a deployed environment you must **rebuild**, not just redeploy.

Those two switch on sign-in and circuit sync. Server-side writes — billing sync, org membership,
exam grading, the hardware quota — additionally need:

```
SUPABASE_SERVICE_ROLE_KEY=eyJ...   # NEVER expose this to a browser
```

Without it, entitlements fall back to free and **every hardware submission is refused**. That is
deliberate fail-closed behaviour on the one endpoint that spends money, not a bug.

## 5. Sign in

Both variables must be non-empty for accounts to switch on. Once they are, the
auth panel on `/circuits` shows an email field and sends a **magic link**. Click
the link in your inbox and the panel switches to a `synced` badge; saves then go
to your Supabase project instead of `localStorage`.

For magic links to work in production, add your deployed origin under
**Authentication → URL Configuration → Redirect URLs**. Local development at
`http://localhost:3000` is allowed by default.

## Behaviour summary

| State | Where circuits are stored | Badge |
| --- | --- | --- |
| No env vars | Browser `localStorage` | `local storage` (amber) |
| Env vars set, signed out | Browser `localStorage` | `local storage` (amber) |
| Env vars set, signed in | Supabase `public.circuits` | `synced` (teal) |

If a Supabase request fails at runtime (offline, project paused), the app falls
back to `localStorage` rather than losing your work or showing an error page.

Share links never touch Supabase at all — the circuit is base64url-encoded
OpenQASM inside the URL itself.
